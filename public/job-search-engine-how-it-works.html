OVERVIEW

The Job Search Engine is an autonomous daily job-hunting assistant built with Python + FastAPI. It scrapes remote jobs from multiple free sources, scores each posting against your resume using Groq's LLaMA 70B, drafts personalized outreach emails for high-scoring matches, and surfaces everything in a React review UI where you read AI reasoning, edit drafts, and approve or skip — nothing sends without your click.

Job Sources → SQLite Storage → Groq AI Scorer → Email Drafter → FastAPI Backend → React UI Review

// 02

DUAL PIPELINE ARCHITECTURE

Two completely isolated pipelines run in parallel — each with its own state, lock, and endpoints. Neither can interfere with the other.

📊 Main Pipeline

Pulls from Remotive API (JSON) and We Work Remotely (RSS). Targets software engineering, backend, and full-stack roles. Results land in the jobs table with a status flow: new → scored → pending → approved → sent | skipped.

Remotive API + WWR RSS → jobs table
🌐 RemoteOK Pipeline

Uses the RemoteOK JSON API — a free, no-auth alternative after Upwork permanently shut down public RSS feeds. Converts search terms to tag strings via a lookup map. Results land in the upwork_jobs table.

RemoteOK API → upwork_jobs table

JOB SOURCES & DEDUPLICATION

How Jobs Are Fetched

Each source is queried with a list of configurable search terms stored in SQLite. The pipeline can be re-run daily — INSERT OR IGNORE on the job_id unique constraint makes every run idempotent. Only new jobs that haven't been seen before enter the scoring queue. The RemoteOK scraper converts human-readable terms like "java backend developer" into API tag strings like "java,backend" via a lookup map.

Search Terms (DB) → HTTP Fetch → Normalize Fields → INSERT OR IGNORE → Score Queue

AI SCORING ENGINE (GROQ)

Every new job is scored 1–10 by LLaMA 3.3 70B against your resume. The model returns structured JSON with a score, plain-English reasoning, key matches, and gaps.

Scoring Prompt → Structured JSON

The prompt injects the full resume text and job description into a single call. Groq's format='json' flag forces structured output. Even so, the response is stripped of any markdown code fences before parsing — a real-world reliability fix since models occasionally wrap JSON in triple-backtick blocks.

SCORING CALL

model: llama-3.3-70b-versatile
temperature: 0.3 (deterministic)
format: json
num_ctx: 4096 (fits resume + JD)

JSON RESPONSE

{ score: 1–10,
  reasoning: "...",
  key_matches: [...],
  key_gaps: [...] }

# src/scorer.py
response = client.chat.completions.create(

  messages=[{"role": "user", "content": prompt}],
  response_format={"type": "json_object"},
  temperature=0.3,
  max_tokens=800,

raw = response.choices[0].message.content
# Strip markdown fences that models occasionally add

EMAIL DRAFTING SYSTEM

Draft → Review → Approve → Send

Jobs scoring ≥ 7 (configurable threshold) automatically get a personalized email draft. The drafting call uses temperature=0.6 for more natural, varied prose. The draft is stored in SQLite with status pending — it sits there until you review it in the UI and click Approve. Nothing is ever sent automatically.

score ≥ threshold → Groq drafts email → status = pending → UI review & edit → Approve → send
# main.py — pipeline loop
for job in get_unscored_jobs():

    update_job_status(job["job_id"], "pending")
  else:
    update_job_status(job["job_id"], "skipped")

WEB REVIEW UI (REACT + FASTAPI)

A left-icon sidebar navigation connects four views. FastAPI serves the built React app as static files in production — no separate web server needed.

SQLITE SCHEMA & STATE MACHINE

WAL Mode + Row Factory

Every connection sets PRAGMA journal_mode=WAL — not just at init. This allows the FastAPI server to read results while the background pipeline is still writing, with no lock contention. row_factory = sqlite3.Row makes rows behave like dicts throughout the codebase.

new → scored → pending → approved → sent / skipped / error
-- Core jobs table (upwork_jobs mirrors same structure)
CREATE TABLE IF NOT EXISTS jobs (
  job_id         TEXT UNIQUE NOT NULL,
  score          INTEGER,            -- 1-10 from Groq
  score_reasoning TEXT,
  email_subject  TEXT,
  email_body     TEXT,
  status         TEXT NOT NULL DEFAULT 'new',
  sent_at        TEXT
);
CREATE INDEX IF NOT EXISTS idx_jobs_score ON jobs(score DESC);

KEY ENGINEERING CHALLENGES

⚡ Upwork RSS Permanently Dead
The original plan used upwork.com/ab/feed/jobs/rss — it returns 404. All alternative Upwork RSS URL patterns also return 404 or a CAPTCHA wall. Upwork permanently discontinued public RSS access. Fixed by switching the entire scraper to the RemoteOK JSON API, which is free, requires no authentication, and covers the same remote-tech job market.
⚡ Groq JSON Fences Breaking Parse
Even with response_format={"type":"json_object"}, Groq's model occasionally wraps the output in triple-backtick code fences (```json ... ```). A naive json.loads() throws a parse error. Fixed by stripping the fence pattern with a regex before parsing, plus a fallback that extracts the JSON object with a broader regex on total failure.
⚡ SQLite WAL Contention
The FastAPI server and the background pipeline both access the same SQLite database. Without WAL mode, the pipeline's write transaction would lock the database and cause the API to return 500 errors during a run. Fixed by setting PRAGMA journal_mode=WAL in every new connection (not just once at init), allowing concurrent reads while the pipeline writes.
⚡ Pipeline State Race Condition
Without locking, two simultaneous clicks on "Run Pipeline" would start two background threads writing to the same rows, causing duplicate scoring and double email drafts. Fixed by checking _state["running"] inside a threading.Lock() acquire block before starting the thread — if already running, return a 409 Conflict response immediately.
⚡ SQLite WAL Files Committed to Git
After the first pipeline run, SQLite creates jobs.db-shm and jobs.db-wal alongside the main database file. These were accidentally staged. Fixed by adding data/*.db* to .gitignore and running git rm --cached to untrack the already-staged files.

ARCHITECTURE SUMMARY

  • ▶ Pipeline layer (Python): fetches jobs from free APIs, deduplicates via SQLite UNIQUE constraints, scores with Groq LLaMA, drafts outreach emails, and logs every run to a run_log table.
  • ▶ Storage layer (SQLite + WAL): two isolated job tables, a queries table for search terms, and WAL mode ensuring zero lock contention between background pipeline and live API reads.
  • ▶ API layer (FastAPI): REST endpoints for both pipelines, pipeline run/status endpoints using background threads with locks, and SPA static file serving in production.
  • ▶ UI layer (React 19 + Vite): left-icon sidebar connecting four views — All Jobs, Saved, Job Filter, and RemoteOK — each with live polling of pipeline status every 3 seconds.
  • ▶ Email layer (smtplib): Gmail App Password authentication over SMTP_SSL port 465. Nothing ever sends without the user clicking Approve in the UI — fully draft-and-review mode.
